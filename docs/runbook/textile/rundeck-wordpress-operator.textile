h1. Rundeck WordPress運用 オペレータ手順書

h2. 概要

Rundeck のプロジェクト *@WordPressControl@* から、WordPress サイト(全34サイト。日本語版 @<site>@ と英語版 @<site>-en@)を運用する手順です。
次の作業を、それぞれジョブ1つで最後まで進めます。本番へは必ず staging(本番データで確認するための環境)を通します。

|_.作業|_.ジョブ|_.何が起きるか|
|開発環境のコンテンツを本番と同じにする|@1-dev-refresh@|本番のバックアップを dev の同名サイトに戻す(*dev の内容は上書き*)|
|staging で本番データを使って確認する|@2-staging@|staging に本番のコピーを置き、昇格予定の更新を当てて、表示を比べる|
|本番へ昇格する|@3-production-promote@|staging の内容で本番 PR を作り、管理者の承認とマージを待って、本番を確認する|
|staging を片付ける|@4-staging-cleanup@|staging からサイトを消す(本番データのコピーを消す)|

ジョブは *あなた自身のアカウント* で動きます(サーバーのユーザー、GitHub、Rancher の権限)。GitHub の PR もあなたの名前で作られます。
WordPress 本体・プラグインの新しい版を dev に入れる作業は、毎週月曜 9:00 に自動で行われます(このジョブでは行いません)。

サイトの確認先(@<site>@ はサイト名。例: @abc@):

|_.環境|_.日本語版|_.英語版|
|dev|@https://<site>.dev.ibid.lan/ja/@|@https://<site>.dev.ibid.lan/en/@|
|staging|@https://<site>.staging.ibid.lan/ja/@|@https://<site>-en.staging.ibid.lan/en/@(staging に置いたときだけ)|
|本番|@https://<site>.production.ibid.lan/ja/@|@https://<site>.production.ibid.lan/en/@|

外部公開のドメインは、本番が @https://<site>.brc.riken.jp/@、dev が @https://wpdev1.brc.riken.jp/@(外部の nginx で表示するサイトを切り替える)です。dev のページ内のリンクは @wpdev1.brc.riken.jp@ を指します。staging は外部公開しません。

|_.項目|_.内容|

|Rancher|Rancher(@https://rancher.brc.riken.jp/@)に FreeIPA でログインでき、@dev1@・@staging1@・@prod1@ のプロジェクト @Wordpress@ が見えること|

権限は次のとおりです。

|_.場所|_.できること|

h2. 初回設定(1回だけ)

自作アプリの手順書で初回設定を済ませている人は、*「4. 動作確認」だけ*行ってください(同じクローン・認証・kubeconfig を使います)。

h3. 1. サーバーにログインする

手元の PC の @~/.ssh/config@ に次を書きます(@<自分のユーザー名>@ は FreeIPA のユーザー名。踏み台(Bastion)にも自分のアカウントで入ります)。

<pre>
Host Bastion
 HostName knowledge.brc.riken.jp
 User <自分のユーザー名>
 IdentityFile ~/.ssh/<自分の鍵>

Host rancher
 HostName 192.168.1.149
 User <自分のユーザー名>
 IdentityFile ~/.ssh/<自分の鍵>
 ProxyCommand ssh -W %h:%p Bastion
</pre>

<pre>
ssh rancher
</pre>

以降の 2〜4 は、rancher にログインした状態で行います。

h3. 2. リポジトリを置いて GitHub に認証する

ジョブは *ホームの @~/ibid-fleet-config@* を使います。場所と名前を変えないでください。

<pre>
git clone https://github.com/silver198545/ibid-fleet-config.git ~/ibid-fleet-config
cd ~/ibid-fleet-config
git config user.name '<GitHubのアカウント名>'
git config user.email '<ID>+<GitHubのアカウント名>@users.noreply.github.com'
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status
</pre>

@user.email@ に入れる値は、GitHub の Settings → Emails の「Keep my email addresses private」の下に出ています。
@gh auth status@ で @Logged in to github.com account <自分のアカウント>@ と出れば OK です。

h3. 3. kubeconfig を置く

# ブラウザで Rancher(@https://rancher.brc.riken.jp/@)に FreeIPA のアカウントでログインする
# クラスタ一覧で @dev1@ を開き、右上の「Download KubeConfig」で保存する。@staging1@・@prod1@ も同じようにする
# 3つを1つにまとめて、rancher の @~/.kube/config@ に置く

<pre>
mkdir -p ~/.kube
KUBECONFIG=~/dev1.yaml:~/staging1.yaml:~/prod1.yaml kubectl config view --flatten > ~/.kube/config
chmod 600 ~/.kube/config
rm ~/dev1.yaml ~/staging1.yaml ~/prod1.yaml
</pre>

確認(どちらも Pod の一覧が出れば OK):

<pre>
kubectl --context dev1 -n wordpress-abc get pods
kubectl --context prod1 -n wordpress-abc get pods
</pre>

*kubeconfig は 30 日で期限が切れます。* ジョブが @Unauthorized@ で止まったら、同じ手順で取り直してください。

h3. 4. 動作確認

Rundeck で @tools/check@ を @env=dev@、@sites=abc@ で実行し、次のように出れば完了です。

<pre>
abc            200  https://abc.dev.ibid.lan/ja/
全サイト正常です。
</pre>

|@1-dev-refresh@|本番のコンテンツ(記事・メディア・設定・ユーザー)を dev の同名サイトに戻す|dev を本番と同じ状態にして確認したいとき|
|@2-staging@|本番と同じ構成・本番データのサイトを staging に置き、昇格予定の更新を当てて、表示を比べる|本番に出す前に*毎回*(staging を通さないと本番へ昇格できない)|

|@3-production-promote@|staging と本番で差分のあるサイトの本番 PR を作り、承認・マージ後に本番を確認する|staging で確認できたあと|
|@4-staging-cleanup@|staging からサイトを削除する|本番へ昇格したら*必ず*|
|@tools/check@|各サイトの WEB の応答(200 か)と Pod の状態を確認する(読むだけ)|いつでも|
|@tools/backup@|今すぐバックアップを取る|dev のみ(本番は管理者が実行)|

h3. オプション

|_.ジョブ|_.オプション|_.既定値|_.説明|
|@1-dev-refresh@|@sites@|(なし)|対象サイト(複数選択可)|
|@1-dev-refresh@・@2-staging@|@fresh_backup@|@yes@|本番のバックアップを今すぐ取るか。*オペレータは本番の権限が無いので、@yes@ でも自動で最新の日次バックアップ(毎日 3:00)を使います*|
|@2-staging@・@2a@・@4@|@site@|(なし)|対象サイト(例: @abc@。英語版は @abc-en@ を別に選ぶ)|

|@3-production-promote@|@sites@|@all@|昇格するサイト。@all@ は staging に載っている、本番にある全サイトのうち差分のあるもの|
|@3-production-promote@|@merge_wait_minutes@|@240@|本番 PR の承認・マージを待つ時間(分)|
|@tools/check@・@tools/backup@|@env@ / @sites@|@production@ / @all@|環境(@production@・@staging@・@dev@)と対象サイト|

h2. 実行方法

h3. A. 開発環境のコンテンツを本番と同じにする(@1-dev-refresh@)

*dev の記事・設定・ユーザーは、本番のもので上書きされます。* dev で作業中の内容が無いか、先に確認してください。

# Rundeck にログインし、プロジェクト @WordPressControl@ を開く
# @1-dev-refresh@ を開き、@sites@ で対象サイトを選んで「Run Job Now」
# 1サイトにつき数分〜数十分(サイトの大きさによる)。最後に次の行が出れば成功: @devの abc abc-en を本番のコンテンツで更新しました。表示・管理画面をブラウザで確認してください。@
# dev の確認先をブラウザで開き、表示を確認する。管理画面には*本番のアカウント*でログインする

上書き前の dev の状態は、ジョブが最初にバックアップしています(戻すときは管理者に依頼)。

h3. B. staging で本番データを使って確認する(@2-staging@)

本番に出すサイトは、毎回ここで確認します。*staging に同時に置けるのは4サイトまで*です。

# @2-staging@ を開き、@site@(例: @web@)を選んで「Run Job Now」(@upgrade=yes@ のまま)
# ジョブが次を順に行う(サイトの大きさによって数十分以上かかる)
#* 本番と同じ構成で、サイトを staging に置く(PR は自動でマージされる)
#* 本番のバックアップを戻し、*比較の基準*(各ページの応答、WordPress・プラグインの版)を記録する
#* dev の構成(昇格予定の更新)に切り替え(PR は自動でマージされる)、プラグインの更新・DB の更新の所要時間を測る
#* 基準と比べて、応答が変わったページ・PHP のエラーを報告する
# 出力の「基準(本番と同じ構成)との比較」を見る。成功なら次の行が出る: @HTTPステータスが変わったページはありません(11ページ)。@
# ブラウザで @https://<site>.staging.ibid.lan/ja/@ を開き、記事・管理画面・プラグインの画面を確認する
# 結果(所要時間・気づいた点)を、本番昇格の PR に書く

問題が見つかったら、dev で直してから @2a-staging-upgrade@ で切り替えからやり直します。

h3. C. 本番へ昇格する(@3-production-promote@)

staging で確認できてから行います。本番に出るのは *staging に載っている内容* です。

# @3-production-promote@ を開き、@sites@ を選んで(staging に載せたサイト、または @all@)「Run Job Now」
# ジョブが本番 PR を作り、CI を待ってから PR に次のコメントを付け、*待ち状態* になる: @本番バックアップは未取得です(実行者に本番でJobを作る権限が無いため)。@
# *管理者に PR の URL を伝えて、「バックアップ → 承認(Approve)→ マージ」を依頼する* (本番のバックアップは、承認する管理者がマージの直前に取ります)
# マージされると、ジョブが自動で続きを行い、本番の確認まで進む。最後に次の行が出れば成功: @本番への昇格が完了しました: abc abc-en ...@
# 本番の確認先をブラウザで開き、表示を確認する

staging と本番に差分が無いときは、PR は作らず本番の確認だけ行って終わります。
staging に無いサイトを選ぶと、「stagingに <site> がありません」で止まります(先に @2-staging@)。

h3. D. staging を片付ける(@4-staging-cleanup@)

本番へ昇格したら、*必ず* 同じ @site@ で @4-staging-cleanup@ を実行します(本番データのコピーを消し、staging の空きを作る)。
昇格をやめた場合も実行します。

h2. 動作の仕組み

h3. @1-dev-refresh@

# 本番の最新の日次バックアップ(毎日 3:00)を選ぶ
# dev の今の状態をバックアップする(上書き前の控え)
# 本番の wp-content と DB を dev の同名サイトに戻す
# DB の中の本番の URL(@<site>.brc.riken.jp@)を dev の URL(@wpdev1.brc.riken.jp@)に置き換える
# 各サイトの応答(200 か)を確かめる

h3. @2-staging@

# 本番と同じ構成で staging にサイトを置く PR を作り、自動でマージする(staging 用のパスワードは毎回新しく作る)
# staging1 にサイトができるのを待ち、本番のバックアップを戻して URL を置き換える
# トップと最近更新された10ページの応答、WordPress・プラグイン・テーマの版を「基準」として記録する
# (@upgrade=yes@)promote ワークフローで dev の構成を staging へ昇格する PR を作り、自動でマージされるのを待つ
# プラグイン同期の Job、DB の更新(@wp core update-db@)、MariaDB のアップグレードを確かめる
# 同じページの応答を取り直して基準と比べ、PHP のエラーを表示する

h3. @3-production-promote@

# staging と本番で差分のあるサイトを調べる(staging に無いサイトは対象外)
# promote ワークフローで staging → 本番の PR を作る(作成者は @ibid-ops-bot@)
# 「本番バックアップは管理者がマージ直前に取る」と PR にコメントする
# *人が PR を承認・マージするのを待つ*(このジョブはマージしない)
# マージされたら、Fleet の反映を待って(約3分)各サイトの rollout を確かめ、本番の応答と MariaDB の状態を確認する

h3. @4-staging-cleanup@

# staging からサイトを消す PR を作り、自動でマージする
# マージされたら、staging1 のサイトの namespace を削除する(DB・wp-content・バックアップも消える)

h2. ログの確認

Rundeck のジョブの実行画面(Log Output)に、すべての出力が残ります。

|_.出力|_.意味|
|@main: <コミット> <メッセージ>@|リポジトリを最新に揃えた|
|@注意: 本番でバックアップのJobを作る権限が無いため、…最新の日次バックアップを使います。@|オペレータの通常の動き(問題ない)|
|@最新の日次バックアップを使います: production/<site> <日時>@|使ったバックアップ|
|@URL置換: <本番のURL> → <devのURL>@|URL の置き換え(続く行に件数)|
|@<site>  200  https://...@|サイトの応答(200 なら正常)|
|@全サイト正常です。@|確認した全サイトが正常|
|@PR作成: https://...@|作った PR|
|@HTTPステータスが変わったページ:@|staging で応答が変わったページ(要確認)|

作られた PR は GitHub の Pull requests でも見られます。本文の最後に「実行者: <あなた>(Rundeck、...)」と入ります。

h2. 注意事項

* *@1-dev-refresh@ は dev の内容を上書きします。* dev で作業中の記事や設定があれば消えます。
* dev のコンテンツを本番に送る方法はありません(本番に出るのは構成=バージョンとプラグインだけ)。
* *staging のサイトは本番データのコピーです。本番へ昇格したら必ず @4-staging-cleanup@ で消してください。* 同時に置けるのは4サイトまでです。
* *本番の PR は自分ではマージできません。* 管理者の承認が必要で、本番のバックアップも管理者が取ります。
* @merge_wait_minutes@ を過ぎてもマージされないと、ジョブは失敗で終わります。PR は残るので、マージ後に @tools/check@(@env=production@)で確認してください。
* 同じジョブは同時に1つしか動きません。
* rancher の @~/ibid-fleet-config@ を手で編集しないでください。未コミットの変更が残っていると、すべてのジョブが最初で止まります。
* 本番(prod1)は見るだけです。本番での操作が必要なときは管理者に依頼してください。
* kubeconfig は 30 日で期限が切れます。
